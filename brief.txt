INFINITE FACTORY OS
Design Brief for Claude Design
An operator UI for the multi-niche autonomous content &amp; monetization system
Prepared by Claude · 2026-04-25
Source: infinite_factory_blueprint_v37.docx + live Airtable read
Contents
1. What we are building
Infinite Factory OS is a single operator surface for the autonomous Instagram affiliate content system that today is run across Airtable, Make.com, fal.ai, Cloudflare Workers, the Instagram Graph API, OpenAI, and Awin. The system already has 35 Airtable tables and 25 Make.com scenarios spread across 6 layers of automation. Operating it currently requires opening four to six different consoles and reasoning across them by hand.
The OS does not replace those backends. It puts a single, business-language UI in front of them so that one person — and eventually a small team and a few collaborating agents — can monitor the system, execute work that needs human judgment, edit prompts and content, and grow revenue across multiple niches without losing the thread.
It must scale across many niches in parallel. Today: one parent niche (Parenting &amp; Family) with five sub-niches (one paused). Within months: more parent niches and dozens of sub-niches. The architecture must be reusable, modular, and non-bespoke.
1.1 Working name and naming alternatives
Working title: Infinite Factory OS. Final name to be chosen by Dave; alternatives to consider:
Factory Floor — emphasises the hands-on, operator-day-to-day feel
Atlas — a single map across niches, scenarios, content, and revenue
Mission Control — frames it as a launch / operations console
CEO Console — keeps the original framing of an executive surface
Studio — ties to the four-content-type creative model
1.2 Why now
The system has matured past the point where ad-hoc inspection of Airtable tables is enough. As of 2026-04-25 there are 293 Ideas, 152 Captions, 104 Assets, ~72 published posts, 7 affiliate offers, 1 active account, 1 storefront site, and 0 sales recorded. The bottleneck is no longer creation; it is decision-making, rework, and routing across surfaces. A purpose-built operator UI moves the limit out from human attention.
2. Audience and use cases
2.1 Primary user
Dave — founder, CEO, and currently the only operator. Already knows every table, scenario, and prompt by name. The OS is built for him first, which means: dense information, technical labels are fine (Airtable IDs, Make scenario IDs, error codes), no marketing polish.
2.2 Future users
Codex — collaborating coding agent that needs to read state and execute structured actions; UI should expose data shapes that an agent can also consume.
Niche operators — once additional niches launch, lower-trust users who manage one niche each.
Stakeholders / partners — a future read-only &quot;investor view&quot; is a v3 concern, not MVP.
2.3 Top jobs to be done
Morning health check: in 30 seconds, see if the factory ran overnight and which scenarios are red.
Approve content: clear the Editor Queue without leaving the OS — preview, edit caption, re-render slide, approve, publish.
Diagnose a broken scenario: see error rate, last execution, recent payloads, and one-click open in Make.com.
Edit a prompt safely: change a system prompt with a versioned snapshot, see diff, roll back if needed.
Grow a niche: launch a new sub-niche from a brief, monitor pipeline filling, see first revenue come in.
Add an offer: paste a URL, watch the intake queue enrich it, decide whether it goes on the storefront and the bio.
See what is making money: weekly per-niche revenue, top offers, cost-per-publish trend.

6. Key screens
Four wireframes follow. They are intentionally low-fidelity — Claude Design will produce the polished mockups; these define structure, density, and content slots.
6.1 Home / Health — hybrid CEO + Operator
The only page where both the operator concerns and the CEO concerns coexist. Left half answers &quot;is the factory healthy?&quot;. Right half answers &quot;is the business growing?&quot;. On smaller viewports, the two halves collapse to tabs.
Components on the operator side:
Layer health row — five chips, one per layer, with status pulled from active blockers + scenario error rates.
Active blockers panel — top 8 with priority, age, and one-click drill into the relevant module or scenario.
Throughput sparkline — 14-day history of Ideas → Captions → Assets → Published. The drop on Apr 25 (S2b stop) should be visually obvious.
Components on the CEO side:
KPI strip — Posts published (30d), Total reach, Affiliate clicks, Net revenue.
Sub-niches table — per sub-niche pipeline depth, posts/wk, reach, status. Includes &quot;Launch new niche&quot; button.
Decisions waiting on you — list of items requiring human input across modules.
Figure 2 · Home / Health — hybrid layout
6.2 Content Pipeline — kanban over the production funnel
Every Idea moves left-to-right through six columns: Ideas → Scripts &amp; Captions → Assets → Editor Gate → Published → Cleanup. Filters at top by sub-niche, content type (VIRAL / AUTHORITY / ENGAGEMENT / SALES — colour-coded with the same tokens used everywhere), and format (Reel / Carousel / Static). Each card is a real Airtable record. Click opens a side drawer with full record + edit + run-scenario actions. Drag between columns triggers a status change with confirmation.
Why kanban: the Make.com pipeline is already a left-to-right flow; mirroring it makes drop-offs (e.g. 293 Ideas vs 152 Captions vs 104 Assets vs 72 Published) immediately visible.
Figure 3 · Content Pipeline — filterable kanban
6.3 Editor Queue — single-screen approval surface
Left rail: queue list. Right pane: full asset detail with carousel preview, caption text, Editor Agent v2 reasoning, audit trail, and an action bar (Approve · Edit caption + retry · Re-render slide · Reject · Skip). Designed so a single review takes ~30 seconds.
Editor Agent v2 reasoning is shown verbatim from Airtable Editor Reviews. Score breakdown (Hook, CTA, Brand Fit, Clarity, Engagement) is rendered as a small radar or bar set. The CTA flag and contamination rule outputs are highlighted because they are the most common rejection reason.
Figure 4 · Editor Queue — list + detail
6.4 Monetization — revenue across niches
Top KPI strip; main chart is per-sub-niche revenue stacked over time once Awin starts reporting; right-hand table lists top offers; bottom-left surfaces the Offer Intake Queue with the current S5g failure mode visible; bottom-right shows the storefront status. This is the page that earns its keep when revenue exists.

9. Design system constraints
9.1 Density and tone
Dense and information-rich. This is a tool, not a marketing surface. Whitespace exists for legibility, not for breathing room. Numbers and IDs are first-class citizens; render IDs in monospace.
No marketing illustrations, no celebratory micro-animations, no gradients on primary surfaces. The system aesthetic is closer to Linear, Stripe Dashboard, or a high-quality internal admin tool than to a consumer SaaS landing page.
9.2 Mode
Dark left navigation + light content area as the default (matches mac-app feel). Full dark mode is v2; full light mode is v2.
9.3 Type scale
Sans-serif system stack (Inter or system-ui), with a monospaced face (JetBrains Mono or system-ui-monospace) for IDs, JSON, and timestamps. Suggested scale:
Display 24/32 — page titles only.
H1 18/24 · H2 14/20 · H3 13/18 — section headers.
Body 13/19 — primary text. Small 11/16 — meta. Caption 10/14 — column labels.
Numbers in KPI cards: 22–28pt bold, with a 11pt label above and a 10pt comparison below.

10. Interaction patterns
10.1 Open-in-source
Every record card and every scenario row has an &quot;open in source&quot; affordance — Airtable record link, Make.com scenario URL, fal.ai job page, GitHub commit, etc. Operators must never feel trapped in the OS; the underlying tools are still the source of truth.
10.2 Run-scenario contract
Anywhere a Make scenario can be triggered: the action shows the scenario ID + name, last execution time, last status, and a confirmation step on click. After triggering, a toast appears and the relevant scenario row goes into &quot;Running&quot; state until polled.
10.3 Edit-with-snapshot contract
Any edit to a Prompt Template, Sub-Niche brief, or Brand voice writes a snapshot to .ai/prompt_versions/ (or equivalent) before the change is committed. The diff is shown in the UI; rollback restores the snapshot. This mirrors the existing rollback discipline established in handoffs.
10.4 Multi-niche scope
Every page that contains data has a niche scope selector at the top right (default: All niches). Selection persists per session. Where appropriate, comparisons are side-by-side rather than concatenated.
10.5 Empty states
All current zero states are real and visible: 0 sales, 0 storefront-eligible offers, 0 hero slides, 0 sections. Empty states must explain (a) what would normally be here, (b) the upstream blocker, and (c) the closest action that would create the first record.
11. MVP vs v2 phasing
11.1 MVP — the five modules that earn their keep today
Build these first because they correspond to active pain or active value:
Home / Health — replaces the morning Airtable + Make.com sweep.
Content Pipeline — replaces filtered Airtable views and gives a visual sense of drop-off.
Editor Queue — clears the daily approval backlog without leaving the OS.
Monetization — even with £0 revenue today, this is the page that makes growth legible.
Brand &amp; Settings — one place to read sub-niches, voices, accounts; required for every other module to make sense.
11.2 v2 — pulled in once MVP earns its place
Niches — niche launch checklist, brand brief generator UI, dedicated overview per sub-niche.
Scenarios — Make.com control surface (run, stop, inspect last 50 executions, see error rates).
Prompts &amp; Agents — versioned prompt editor with diff and rollback.
Performance — per-post and per-niche metrics with engagement trends.
Learning Insights — winning hooks/formats, weekly insight rollups.
Offers &amp; Intake — manual scoring of offer intake queue, bio-link priority management.
Storefront — site builder UI, hero slide editor, feed rebuild.
11.3 v3 and beyond
Stakeholder / investor read-only dashboard.
Per-niche operator role with scoped permissions.
Agent-facing structured endpoints so Codex can read state programmatically.
